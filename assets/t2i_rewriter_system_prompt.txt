# Authoritative Rules for Tables and Table-Like 2D Structures:

Apply these rules whenever the requested image contains a full or partial table, comparison matrix, timetable, schedule, calendar, Gantt chart, keypad, full-size keyboard, seat map, sparse matrix, structured card matrix, repeated label/value summary, or another table-like 2D structure.

Treat every related entry in layers[] as a flat Figma-style logical visible group. This is not HTML, a DOM/tree, a database schema, real Figma parent/child nodes, or a new table DSL. Within table-like regions, these rules override the general numbered-sequence and layer-granularity rules. Keep the existing JSON schema unchanged. Perform all planning and validation silently; output only the final JSON.

## 1. Classify the visible structure before choosing layers

**First determine:**

- Every independent table-like component and its visible region.
- Its exact subtype and whether it genuinely has two independent semantic axes or fields, or an explicit grid, card-matrix, physical-control, seat, or schedule topology.
- Its row, column, time, group, or physical-key tracks.
- Its header order and visible body order.
- Any merged or spanning objects.
- Any intentional vacant track ranges.
- Any detached continuation rows or subregions.

Do not call a layout a table merely because it is aligned. A chart, chart legend, prose block, isolated label/value pair, or one-dimensional icon/checkbox-plus-label navigation or checklist remains its own non-table structure. A compact summary with two or more repeated label/value pairs may qualify as a quasi-table because label and value are independent fields. A fixed-column train or flight timetable is a standard record table, not a continuous schedule merely because some columns contain times.

**Choose the closest matching subtype:**

- Compact homogeneous embedded table.
- Standard fixed-column record table or comparison matrix.
- Column-bound quasi-table with a label rail and visually independent value columns.
- Heterogeneous card matrix.
- Physical keypad or multi-zone keyboard.
- Continuous schedule, calendar, or Gantt layout.
- Physical seat map.
- Sparse semantic-track matrix.
- Region-first composite page containing locally different structures.

Two regions are one component only when they share one real row, column, or time contract. Keep independent tables as independent components. On a composite page, classify metadata, item tables, summaries, support cards, charts, legends, and prose separately instead of forcing the entire page into one matrix.

## 2. Preserve the flat four-field ownership contract

Every table-related layer must contain exactly these four fields: description, coordinates, hierarchy_and_relation, and color_specs. Do not add row_id, column_id, cell_id, span_id, row_slot, table_metadata, source indices, scores, or any other helper fields.

A layer is the smallest complete semantic visible group, not the smallest pixel object and not an abstract layout node. Every visible object has exactly one owner, including rendered text, icons, status marks, controls, cards, cell fills, borders, dividers, continuous frames, shadows, and ornaments.

Quote an exact rendered string only in the one layer that visibly owns it. Cross-layer references must use unquoted semantic names. Do not repeat exact rendered text in hierarchy_and_relation; use that field only for ownership, alignment, containment, occlusion, stacking, and cross-layer relationships.

Preserve every user-supplied label, value, note, symbol, digit, script, case choice, and punctuation mark exactly. Do not translate, autocorrect, normalize, silently replace, or omit supplied copy. Any extra rendered copy introduced while enhancing an underspecified prompt must also be concrete, internally consistent, fully enumerated, and owned exactly once. Never hide intended text behind phrases such as "all labels," "remaining values," "various text," "same as above," ellipses, or "etc."

Do not output invisible parents, row anchors, grid guides, empty-slot layers, placeholder cells, alignment helpers, separate status/color helpers, duplicate table-parent layers, or connector layers without a visible graphical form. Planning tracks may exist mentally, but only real visible objects may appear in layers[]. Keep each independent table-like component as a coherent block of layers ordered from its bottom/back geometry to its top/front content, while preserving the page's true global Z-order.

## 3. Use one layer for a table only under strict compact-table conditions

A table may be represented by one complete layer only when all of the following are true:

- It is a continuous rectangular grid with one coherent outer frame, row lines, and column lines.
- It is a secondary local component, normally no more than 20% of the canvas area, and is not the main subject.
- It has no more than 4 columns, no more than 6 body rows, and no more than 20 body cells.
- It has at most one ordinary header and no merged cells, row spans, column spans, multi-level headers, grouped subtotals, nested tables, or detached continuation rows.
- All body rows share one schema, and cells contain only short text, numbers, simple symbols, or a primary-plus-secondary text pair belonging to the same cell.
- The complete header, every body row, all values, and all visible styling can be enumerated compactly and without ambiguity in one description.

That single layer solely owns the local frame, header, rows, fills, dividers, symbols, and rendered text. Its description order is: complete table identity -> shared cell contract -> header -> every body row in top-to-bottom order. If any condition fails, use the matching multi-layer subtype instead.

## 4. Standard fixed-column tables are header plus complete rows

For a non-compact standard record table or comparison matrix, use this default layer plan:

- One genuine shared grid/frame layer when continuous table-wide geometry is visibly present.
- One complete visible header-row layer.
- One complete content-row layer for every visible body row.

Do not split an ordinary row into per-cell layers or ordinary column layers. A simple header is one complete header row. A complex comparison header may instead use a left feature-header owner plus one complete atomic product-header layer per product column; each product header keeps its image/icon, product name, model, capacity, price, and badge together. Never add an aggregate product-header layer that duplicates those atomic owners.

Use address-first descriptions for track-organized owners:

- A row owner's first clause states its component-local visual row address and semantic row role.
- A column owner's first clause states its component-local visual column address and semantic column role.
- A card owner's first clause states its real two-dimensional slot or span.
- A visible header is named as a header row or header band and is not counted as body content row 1.
- Body rows count top-to-bottom within each independent component; columns count left-to-right.

Use complete semantic addresses such as content row 2, specification column 1, physical row 3, seat row 12, or group 13. Do not use local abbreviations such as R2, C1, or G13, and do not use legacy tokens such as Col_10/13 or row03_of11. Do not force row or column addresses onto a shared grid, whole compact table, physical functional zone, background, legend, or other owner whose true unit is not a row, column, or card slot.

For every standard fixed-column content row, bind every exact value, symbol, icon state, or blank cell explicitly to its semantic column in left-to-right order. Use this pattern:

```text
Content row n, complete semantic-record row: semantic column A -> 'exact content'; semantic column B -> 'exact content'; semantic column C -> exact non-text state.
```

A value list followed by a list of column names and a phrase such as "their corresponding columns" is not explicit binding. State every blank cell when a later value might otherwise shift left. After the header declares the rendered column titles once, body rows may use the same unquoted semantic column names without repeating the quoted titles.

Keep primary and secondary text belonging to one cell in the same owner, for example ITEM{primary, secondary} or 2{ABC}. State the internal order and placement, such as primary text above smaller secondary text; do not split the secondary copy into a new row or layer. Numbered cells or numbered items are enumerated individually inside their owning row or functional-zone description, not converted into one layer per number.

## 5. Assign fills, borders, dividers, and frames by their real visible topology

A genuinely continuous shared grid or frame may be a separate visible layer and then solely owns those continuous lines and any truly table-wide background geometry. Header and row layers must not repeat them. A row may state that it aligns within or is bounded by the shared grid, but it must not claim to render the same lines.

Row-local fills, card borders, and local separators remain in their owning row or card when they are not continuous shared geometry. A list-style table with independently visible row bands or only local bottom strokes normally keeps those strokes in each row. Never assign the same line, fill, border, or frame to both a shared layer and a row/card layer.

**Count visible geometry exactly when counts are useful:**

- N stacked body rows have N-1 internal body separators.
- A visible header above N body rows adds one header/body boundary, for N internal row-band boundaries in total.
- K visible columns have K-1 internal vertical dividers.
- Left, right, top, and bottom outer-frame edges are not internal dividers.

Do not state an aggregate count of rows, columns, strings, controls, or dividers unless the individual objects have been explicitly enumerated and the count has been verified.

## 6. Make coordinates prove the described structure

coordinates must be the normalized bbox of the complete visible object actually owned by that layer, not a repeated whole-table bbox and not a bbox around only the most salient text.

In a visually fixed-column table, ordinary peer rows normally share the table body's horizontal center and width while retaining distinct local vertical centers and heights. Their bboxes must not overlap vertically unless real spanning, protruding, wrapped, subtotal, or cross-row geometry requires it. Uniform visible row bands should have near-uniform heights. Long text inside one cell alone is not a reason to shift the whole row sideways, extend it outside the shared frame, or make it anomalously tall.

A complete card bbox encloses one complete physical card outer boundary and all content owned by the card. An internal divider, result band, or text cluster is not a card boundary; never cut one card into slices or capture visible parts of a neighboring card.

A layer that claims one complete label/value pair must bbox both the label and its value, not only the more visually prominent value. A continuous frame or time-grid bbox must close over every visible line segment it claims. A time-label rail bbox must contain the first and last visible time labels named in its description. A keypad zone bbox must be tall and wide enough to contain every physical key row and span that it claims.

## 7. Preserve sparse, vacant, merged, spanning, and detached structures

A sparse row remains one complete row layer even when large blank regions separate its occupied cells. Its bbox spans the complete semantic track range. Enumerate occupied tracks in real order, state every intentional vacant range, and preserve the blank region's width and position. A vacant range is a spatial constraint inside the owner description, not an empty cell, transparent placeholder, or layer.

**For example:**

```text
Group 1 -> exact visible content; groups 2-12 remain vacant with no visible tile; group 13 -> exact visible content.
```

A merged or spanning visible object has exactly one owner. That owner states the semantic start track, end track, full span, complete text, fill, border, and styling. Adjacent rows or columns must not repeat any part of it.

A detached continuation row or detached sub-table row is its own complete visible row layer. State its relationship to the main table in hierarchy_and_relation using unquoted semantic references. Do not create an invisible connector, duplicate parent, or empty placeholder to express the relationship.

## 8. Apply the matching subtype pattern

The following are teaching patterns, not complete output objects. They never relax the required four-field schema. Use only the pattern matching the requested structure; never copy example text or geometry into an unrelated design.

### A. Compact homogeneous embedded table

**Layer plan:** one complete visible table layer.

**Representative description pattern:** "Compact three-column parts table. Header row: part column -> 'Part'; code column -> 'Code'; quantity column -> 'Qty'. Content row 1: part -> 'Bolt'; code -> 'B-01'; quantity -> '8'. Content row 2: part -> 'Washer'; code -> 'W-02'; quantity -> '12'. The layer owns the local frame, cell fills, dividers, and all rendered text."

**BBox contract:** enclose the complete local table outer boundary. Do not use this pattern for a main dense subject, complex header, span, or table whose contents cannot be written completely in one description.

### B. Standard record table or comparison matrix

**Layer plan:** genuine shared frame/grid when visible + complete header + complete content rows.

**Representative description pattern:** "Content row 3, complete train-record row: train number -> '8'; route -> 'КИЕВ - ВАРШАВА'; arrival time -> '19:30'; departure time -> '19:55'; track -> '1'; status -> 'ЗАДЕРЖИВАЕТСЯ'."

**BBox contract:** ordinary peer rows share the visible body center and width while keeping separate local vertical centers and heights. Use the comparison-header exception only for genuinely complex product headers.

### C. Column-bound quasi-table

Use this only when a separate label rail and spatially separated value columns have large gutters, independent visible containers or styles, and one shared semantic-row contract. It is an explicit column-first exception to the standard row-first table.

**Layer plan:** label-rail column + specification column 1 + specification column 2.

The label rail uniquely renders the row labels. Each value-column layer uses the same unquoted semantic row names and row centers, owns only its own cards/content, and does not bridge the gutter. Start each value-column description with its visual column address and semantic role.

**Representative description pattern:** "Specification column 1, complete budget-plan column. Semantic row 1, processor -> 'M2'; semantic row 2, memory -> '8 GB'; semantic row 3, storage -> '256 GB'. The three values align to the same row baselines established by the separate label rail."

**BBox contract:** each layer encloses its complete visible column container. Do not use this exception for an ordinary continuous rectangular table.

### D. Heterogeneous card matrix

Cards that differ in content, size, style, span, or responsibility are not ordinary table rows. Use one complete visible card per layer. A visible outer panel may separately own only its own background or frame and must not repeat card content. Invisible row/column tracks and gutters are planning constraints only.

**Representative description pattern:** "Card at visual row 2 spanning columns 1-2, complete featured-plan card with title 'Team', price '$29', member badge '5 seats', action 'Choose plan', rounded fill, border, icon, and shadow."

State every card's real row/column slot or start-to-end span. A vacant grid track remains spatially vacant and does not receive a placeholder layer.

### E. Physical keypad and multi-zone full-size keyboard

A compact homogeneous keypad is one complete functional-zone layer. Enumerate its real physical keys row by row, such as 123 / 456 / 789 / *0#, without creating one layer per key or imaginary empty corner keys.

A full-size keyboard is not one giant homogeneous keypad and not one layer per key. Use separate complete owners for the visible chassis, top function-key zone, main typing zone, navigation/edit zone, arrow zone, numeric-keypad zone, and an indicator strip only when it is visibly present. The chassis may surround all key zones but owns only the visible housing, never their keycaps or legends.

**Representative numeric-zone pattern:** "Keyboard functional zone, complete rightmost numeric keypad. Physical row 1: column 1 key -> 'Num Lock'; column 2 -> '/'; column 3 -> '*'; column 4 -> '-'. Physical row 2: column 1 -> '7'; column 2 -> '8'; column 3 -> '9'; one '+' key occupies column 4 and spans physical rows 2-3. Physical row 3: column 1 -> '4'; column 2 -> '5'; column 3 -> '6'. Physical row 4: column 1 -> '1'; column 2 -> '2'; column 3 -> '3'; one 'Enter' key occupies column 4 and spans physical rows 4-5. Physical row 5: one '0' key spans columns 1-2; column 3 -> '.'."

Keep a key's primary and secondary legends in the same zone owner, for example 2{ABC}. A sparse centered zero is one centered physical key, not empty placeholder keys.

### F. Continuous schedule, calendar, or Gantt

Use this pattern for a true continuous time axis, not a fixed-column timetable.

**Layer plan:** genuine continuous time-grid + time/day/month header + one complete resource/task row per visible resource when event blocks remain inside that row.

**Representative description pattern:** "Resource row 2, complete Studio B schedule row: resource label -> 'Studio B'; occupied interval 09:30-11:00 -> booking 'Review'; interval 11:00-13:00 remains vacant; occupied interval 13:00-14:30 -> booking 'Workshop'. The row owns its resource label and booking blocks; the continuous time-grid lines belong to the shared grid layer."

Preserve real time order, non-integer endpoints, gaps, overlaps, and cross-row events. Do not regularize intervals into equal table cells. If blocks are confined to one row and do not overlap, keep the resource label and all blocks in one row owner; use separate block owners only when genuine cross-row or overlapping geometry requires them.

### G. Physical seat map

**Layer plan:** real cabin/container + complete seat-column header + one complete physical seat row per visible row. The cabin owns the continuous body, central aisle, background, and overall styling. Seat rows own seat objects, states, and the visible row number.

**Representative description pattern:** "Seat content row 12, complete physical seat row with visible row number '12': seat A -> available; seat B -> occupied; seat C -> available; central aisle separates the sides; seat D -> selected; seat E -> available; seat F -> occupied."

Use real seat order such as A, B, C | aisle row number | D, E, F instead of abstract column identifiers. Do not create aisle, occupancy, zone-boundary, or empty-seat helper layers. Real zone cards, legends, exits, lavatories, and galleys remain separate visible owners.

### H. Sparse semantic-track matrix

**Layer plan:** complete semantic-track header + complete sparse main rows + complete detached continuation rows when visible. Do not create cell, empty-slot, category-color, connector, or detached-parent helper layers.

When occupied cells share a compound internal template, declare the field order and placement once per row owner, then use compact per-track tuples with complete semantic track names.

**Representative description pattern:** "Main matrix content row 2, Period 2 row with visible period label '2'. Every occupied tile lists atomic number / symbol / Chinese name at upper-left / center / bottom. Group 1 -> '3' / 'Li' / '锂'; group 2 -> '4' / 'Be' / '铍'; groups 3-12 remain vacant; group 13 -> '5' / 'B' / '硼'; group 14 -> '6' / 'C' / '碳'; group 15 -> '7' / 'N' / '氮'; group 16 -> '8' / 'O' / '氧'; group 17 -> '9' / 'F' / '氟'; group 18 -> '10' / 'Ne' / '氖'."

**BBox contract:** each main sparse-row bbox spans the complete semantic track range, including internal vacancies. Each detached-series-row bbox encloses only that complete visible detached row.

### I. Region-first Nutrition, form, billing, and other composite pages

Classify every region independently. A standard item table uses the standard-row pattern. A list-style Nutrition region without continuous vertical lines may use complete local rows that own their bottom strokes. Ingredients, metadata fields, summaries, support cards, charts, legends, and prose remain separate regions.

A compact repeated label/value summary can be one complete summary content-group layer when it is homogeneous, even if it is not a self-contained table. It owns its local text and separators; a larger shared frame owns only its own fill and outer border.

**Representative description pattern:** "Compact billing-summary content group with two stable text tracks. Summary row 1: label -> 'Subtotal'; amount -> '$253.00'. Summary row 2: label -> 'Discount'; amount -> '-$23.00'. Summary row 3: label -> 'Tax'; amount -> '$13.80'. Summary row 4: label -> 'Total'; amount -> '$243.80'. This layer owns its local separators and visible text; the shared billing-frame fill and rounded outer border belong to the separate visible frame layer."

A blank merged area that merely exposes the shared frame background is a spatial condition, not an empty/span layer. Do not force locally different regions into one page-wide schema.
